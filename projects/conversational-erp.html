Conversational AI for college ERP data

Global InfoVentures Pvt. Ltd. · Assistant AI Engineer, team project · natural-language interface over institutional ERP systems

The problem

Administrative staff need answers that already exist in an ERP database — fee status, library issues, employee records, admissions — but getting them means knowing which module to open and which report to run. The obvious fix is to let people ask in plain language and generate SQL from it.

The obvious fix is also the dangerous one. A language model emitting raw SQL against a live institutional database puts an unpredictable component directly on the write path of records about real students. The design question is how much of the query the model is allowed to author.

The decision that shapes everything else

The model does not write SQL. It emits fields and conditions as structured JSON, and a deterministic payload builder turns those into the actual query — applying alias mappings, default filters and joins before handing the result to the ERP's own web service, which owns the data and executes against it.

This narrows the blast radius considerably: the model cannot invent a table, a join or a destructive statement, because it never gets to express one. The honest limit is that conditions still travel as SQL fragments, joined and passed through. Prompt instructions are the control there, not a grammar or an allow-list. Closing that gap with an explicit condition grammar is the single change I would make first.

Routing before retrieval, retrieval before generation

A Rasa intent classifier picks the module — student, employee, library, fee — before any retrieval or model call happens. A second Rasa bot disambiguates the genuinely ambiguous case, student versus employee, where the same question shape applies to both. If the model still finds the question ambiguous, it asks a clarifying question instead of guessing, and the conversation continues on the server.

This ordering is deliberate and it is a cost decision as much as an accuracy one. Classification is fast and cheap; it runs first and narrows what follows. By the time the language model is invoked it sees one module's schema rather than the whole institution's, which makes the generation task smaller and the prompt shorter.

Only then does retrieval run: the question is embedded with a 384-dimension sentence model, schema fields are retrieved from a Milvus collection, and matching few-shot examples are pulled dynamically. Because schema aliases are stored per institution rather than written into prompts, the same pipeline serves several institutions with different column names and no per-institution prompt forks.

Trade-offs I would defend, and one I would not

Structured output over raw SQL — defensible, and described above. The ERP builds the FROM clause and the joins; the model contributes intent, not syntax.

Per-institution alias collections over per-institution prompts — defensible. Adding an institution becomes a data task rather than a prompt-engineering task. The cost is that a schema change needs a collection rebuild, and a stale alias fails quietly rather than loudly.

Exact-match payload caching — not defensible as built. A cache hit requires zero embedding distance, which makes it an exact-match cache wearing a vector database's clothes, and a hit still re-runs against the ERP because result rows are not cached. It is also not keyed by institution. Either key it properly and cache results, or delete it; as it stands it adds a lookup and buys nothing.

Swallowed audit-insert failures — not defensible. Every interaction attempts an audit row, but a failed insert is logged and dropped, so the trail is best-effort. For a system answering questions about student records, the audit trail should be as durable as the answer.

Voice as an output mode, not an architecture

Speech is a client concern. The service exposes transcription, query processing, clarification, module selection and feedback as ordinary HTTP endpoints; synthesized audio is produced where it makes sense and omitted where it does not. Keeping the voice layer at the edge means the whole query pipeline is testable with text and a terminal, which is how it was actually developed.

Hardening it into a product

After the production deployment I rebuilt the codebase as a self-contained product between 9 and 17 November 2026: four major releases, run as a rehearsal against a fictional institute and a stand-in ERP that executes each generated query over a seeded store of synthetic records, so no real data is involved. Four decisions carry most of the weight.

Identity comes from the ERP, not the request. The API used to trust the institute and user IDs sent in the request body. An API key per client would not identify the user or limit their modules, and server sessions would duplicate a login the ERP already owns. Instead the caller’s institute, user and modules come only from a token the ERP signs with a per-institute secret, with the algorithm pinned, the audience checked, the lifetime capped at 15 minutes and short secrets refused. A client written from the specification alone, sharing no code, was accepted, and its wrong-audience, over-lifetime, other-institute and unsigned tokens were all rejected.

A guardrail on every fragment the model writes. This closes much of the gap named above, short of a full grammar: every SQL fragment Gemini produces is now also validated before the ERP sees it, and rejected on statement separators, comments, UNION, unknown tables in subqueries or protected fields. Fine-tuning was not an option without a labelled set. A golden replay suite freezes the exact payloads, and it caught a duplicated column in top-n fee answers before that release went out.

No institute can see another’s schema. Switching databases on a shared Milvus connection, while searches run in threads, could hand one institute’s field mappings to another. A global lock would serialise every request, and a process per institute costs too much memory, so each database gets its own connection. With two tenants seeded, 126 interleaved concurrent searches returned exactly what the same searches returned one at a time.

Release gates for the parts that are models. A changed model or embedding can silently change routing or retrieval, and manual spot checks do not catch that. Every release must pass embedding parity against a stored reference, accuracy floors for both Rasa routers on held-out sets, Rasa’s data validation, routing stories for each module and a live check of the configured models; then the deploy runs a smoke test and rolls back automatically. One deploy whose script had lost its executable bit failed and rolled itself back, and CI now checks for that too.

The rebuild also moved clarification state to the server, so the browser holds only an ID and never the prompt or the schema, and added a browser interface served by FastAPI: typed or spoken questions, sortable tables with CSV export, inline clarifications and feedback on every answer.

Results and what is measured

In production use, measured by hand: intent classification was close to 100% across more than 50 voice variations per module; field-level schema mappings plus Milvus suggestions raised SQL precision by more than 30%, and vector-based disambiguation of fields and values by more than 40%. The current schema maps 254 employee, 183 student and 74 fee fields.

On every release, reproducibly: 98 automated tests, routing stories passing 6 of 6 for the primary router and 2 of 2 for the secondary, embedding parity at a worst-case cosine of at least 0.9999 against the reference, and Rasa accuracy floors of 0.90 and 0.80, which are gates rather than measured scores. What still does not exist is an end-to-end accuracy benchmark on a labelled question set, split by stage; the rate at which the guardrail rejects what the model produced remains the number that would say most about the structured-output decision.

What this demonstrates

Deciding where a language model's authority ends. The interesting work is the boundary: classification narrows the problem, retrieval grounds it, the model contributes structured intent, and deterministic code — not the model — constructs anything that touches the database.
